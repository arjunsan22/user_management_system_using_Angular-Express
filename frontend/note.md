Tap and Pipe in Observable


🚰 ഒരു വാട്ടർ പൈപ്പ്ലൈൻ ഉപമ (Analogy)

നിങ്ങളുടെ വീടിന്റെ മുകളിലെ ടാങ്കിൽ നിന്നും താഴത്തെ അടുക്കളയിലേക്ക് വെള്ളം വരുന്ന ഒരു പൈപ്പ് (Pipe) ഉണ്ടെന്ന് വിചാരിക്കുക.
• ടാങ്കിൽ നിന്നുള്ള വെള്ളമാണ് API ഡാറ്റ (Observable).
• അടുക്കളയിലെ ടാപ്പാണ് Subscribe ചെയ്യുന്ന കമ്പോണന്റ് (Component).
1. pipe() (പൈപ്പ് ലൈൻ):
ടാങ്കിൽ നിന്ന് ടാപ്പിലേക്ക് വെള്ളം എത്തുന്നതിനിടയിൽ നിങ്ങൾക്ക് ഒരു വാട്ടർ ഫിൽട്ടറോ അല്ലെങ്കിൽ പ്രഷർ കൂട്ടാനുള്ള മെഷീനോ ഘടിപ്പിക്കണമെങ്കിൽ നിങ്ങൾ എവിടെ വെക്കും? ആ പൈപ്പിന് ഉള്ളിൽ വെക്കും അല്ലേ? അത് തന്നെയാണ് Angular-ലെ pipe(). ഡാറ്റ കമ്പോണന്റിലേക്ക് എത്തുന്നതിന് മുൻപ്, അതിനിടയിൽ വെച്ച് ചില ഓപ്പറേഷൻസ് നടത്താനുള്ള ഒരു വഴിയാണ് pipe().
2. tap() (വെള്ളം കുടിക്കാതെ തൊട്ടുനോക്കുക - Spy ചെയ്യുക):
പൈപ്പിലൂടെ വെള്ളം ഒഴുകിപ്പോകുമ്പോൾ, ആ വെള്ളം കുടിക്കാതെ (ഡാറ്റയ്ക്ക് യാതൊരു മാറ്റവും വരുത്താതെ), വെള്ളത്തിന് ചൂടുണ്ടോ എന്ന് അറിയാൻ നിങ്ങൾ പുറത്തുനിന്ന് പൈപ്പിൽ ഒന്ന് തൊട്ടു നോക്കുന്നു. അല്ലെങ്കിൽ ഒരു മീറ്റർ വെച്ച് വെള്ളത്തിന്റെ അളവ് നോക്കുന്നു. ഇതാണ് tap(). ഡാറ്റ കമ്പോണന്റിലേക്ക് പോകുന്ന വഴിക്ക്, അതിനെ യാതൊരു മാറ്റവും വരുത്താതെ (Side-effect), നമുക്ക് ആവശ്യമുള്ള ഒരു കാര്യം ചെയ്യാൻ (ഇവിടെ സിഗ്നലിലേക്ക് ഡാറ്റ സേവ് ചെയ്യാൻ) tap() സഹായിക്കുന്നു.

💻 നിങ്ങളുടെ കോഡ് വെച്ച് നോക്കാം:

typescript
return this.http.post<LoginResponse>(...).pipe( 
  tap((response) => { 
    if (response.success && response.data) { 
      this._currentUser.set(response.data); // <-- ഇതാണ് Side Effect
    } 
  }) 
);
Use code with caution.

1. എന്തിനാണ് ഇവിടെ pipe() ഉപയോഗിച്ചത്?

ലോഗിൻ ചെയ്യുമ്പോൾ കിട്ടുന്ന ഡാറ്റ നേരിട്ട് കമ്പോണന്റിലേക്ക് (LoginComponent) പോകുന്നതിന് തൊട്ടുമുൻപ്, അതിനിടയിൽ വെച്ച് നമുക്ക് സിഗ്നലിലേക്ക് ആ ഡാറ്റ ഒന്ന് കോപ്പി ചെയ്യണം. അതിനുള്ള ഒരു ടണൽ (Tunnel) അല്ലെങ്കിൽ പൈപ്പ് ലൈൻ ആയിട്ടാണ് ഇവിടെ pipe() വർക്ക് ചെയ്യുന്നത്.

2. എന്തിനാണ് അതിനുള്ളിൽ tap() ഉപയോഗിച്ചത്?

API-ൽ നിന്ന് വരുന്ന യൂസർ ഡാറ്റയെ ഒട്ടും മാറ്റം വരുത്താതെ കമ്പോണന്റിലേക്ക് വിടണം. എന്നാൽ പോകുന്ന വഴിക്ക് ആ ഡാറ്റയുടെ ഒരു കോപ്പി എടുത്ത് നമ്മുടെ സിഗ്നലിലേക്ക് (_currentUser.set()) സേവ് ചെയ്യുകയും വേണം.
• tap() ഇല്ലെങ്കിൽ എന്ത് സംഭവിക്കും? നമ്മൾ കമ്പോണന്റിൽ ചെന്ന് subscribe() ചെയ്യുമ്പോൾ മാത്രമേ ഡാറ്റ കിട്ടൂ. പക്ഷേ നമുക്ക് കമ്പോണന്റിൽ മാത്രമല്ല, ഈ സർവീസിന്റെ ഉള്ളിലും ആ ഡാറ്റ സൂക്ഷിക്കേണ്ടതുണ്ട്.
• മാറ്റം വരുത്തുന്നില്ല: tap() ഡാറ്റയെ മാറ്റുന്നില്ല, ജസ്റ്റ് നോക്കുന്നു (Spy ചെയ്യുന്നു). (ഡാറ്റ മാറ്റണമെങ്കിൽ നമ്മൾ map() എന്ന മറ്റൊരു ഓപ്പറേറ്റർ ആണ് ഉപയോഗിക്കുക).

💡 ചുരുക്കത്തിൽ:

• pipe() എന്നാൽ API ഡാറ്റ പോകുന്ന വഴി മധ്യേയുള്ള ഒരു കണക്ഷൻ പൈപ്പ് ആണ്.
• tap() എന്നാൽ ആ പൈപ്പിലൂടെ പോകുന്ന ഡാറ്റയെ തൊട്ടുനോക്കി, ബാക്ക്ഗ്രൗണ്ടിൽ മറ്റൊരു ജോലി (സിഗ്നൽ അപ്ഡേറ്റ് ചെയ്യൽ) ചെയ്യിക്കാൻ ഉപയോഗിക്കുന്ന ടൂൾ ആണ്.
ഇപ്പോൾ pipe()-ഉം tap()-ഉം എന്തിനാണ് ഉപയോഗിച്ചതെന്ന് വ്യക്തമായോ? അതോ ഇതിൽ കൂടുതൽ സംശയങ്ങൾ ഉണ്ടോ?

---- provideAppInitializer -----------------------

ആംഗുലർ ആപ്പ് സ്റ്റാർട്ട് ചെയ്യുമ്പോൾ ബാക്ക്ഗ്രൗണ്ടിൽ യൂസർ ലോഗിൻ ചെയ്തിട്ടുണ്ടോ എന്ന് പരിശോധിക്കാൻ ഉപയോഗിക്കുന്ന initializeAuth() ഫങ്ക്ഷന്റെ പൂർണ്ണമായ വിവരണം താഴെ നൽകുന്നു.
പ്രത്യേകിച്ച്, ഇതിൽ ഉപയോഗിച്ചിരിക്കുന്ന firstValueFrom എന്താണെന്നും അത് ഇവിടെ എന്തിനാണ് ഉപയോഗിച്ചതെന്നും ലളിതമായി മനസ്സിലാക്കാം.

🧠 firstValueFrom എന്നാൽ എന്താണ്?

ലളിതമായി പറഞ്ഞാൽ, RxJS Observable-നെ ഒരു ജാവാസ്ക്രിപ്റ്റ് Promise ആക്കി മാറ്റാൻ ഉപയോഗിക്കുന്ന ഒരു ടൂൾ ആണ് firstValueFrom.
• Observable (ഒരു ടാപ്പ് പോലെ): ആംഗുലറിലെ HttpClient നമുക്ക് തരുന്നത് ഒരു Observable ആണ്. ഇതിൽ നിന്നും ഡാറ്റ കിട്ടണമെങ്കിൽ നമ്മൾ സാധാരണയായി .subscribe() ചെയ്യണം. ഇത് തുടർച്ചയായി ഡാറ്റ തന്നുകൊണ്ടിരിക്കാൻ സാധിക്കുന്ന ഒന്നാണ്.
• Promise (ഒരു കൊറിയർ വരുന്നത് പോലെ): ഒരു തവണ മാത്രം നടന്ന് തീരുന്ന കാര്യങ്ങൾക്കാണ് Promise ഉപയോഗിക്കുന്നത് (ഒന്നുകിൽ സക്സസ് ആകും, അല്ലെങ്കിൽ പരാജയപ്പെടും).

❓ ഇവിടെ എന്തിനാണ് firstValueFrom ഉപയോഗിച്ചത്?

ആംഗുലർ ആപ്പ് ലോഡ് ആകുന്നതിന് മുൻപ് ചില കാര്യങ്ങൾ നടക്കണം എന്ന് പറയാൻ നമ്മൾ APP_INITIALIZER എന്ന ഫീച്ചർ ഉപയോഗിക്കാറുണ്ട്. ആംഗുലറിന്റെ നിയമപ്രകാരം APP_INITIALIZER-ന് ഉള്ളിൽ എഴുതുന്ന ഫങ്ക്ഷൻ ഒന്നുകിൽ ഒരു Promise അല്ലെങ്കിൽ ഒരു Observable റിട്ടേൺ ചെയ്യണം. എന്നാൽ ആ ഫങ്ക്ഷൻ പൂർണ്ണമായി നടന്നു തീരുന്നത് വരെ (അതായത് സെർവറിൽ നിന്ന് യൂസർ ഡാറ്റ വരുന്നത് വരെ) ആംഗുലർ ആപ്പിന്റെ ബാക്കി ലോഡിങ് തടഞ്ഞു വെക്കും (Block ചെയ്യും).
HttpClient തരുന്ന Observable അങ്ങനെ സ്വയം "പൂർണ്ണമായി തീരുന്ന" ഒന്നല്ല. അതുകൊണ്ട് ആംഗുലറിന് കൺഫ്യൂഷൻ വരാതിരിക്കാൻ, "സെർവറിൽ നിന്ന് വരുന്ന ഏറ്റവും ആദ്യത്തെ വാല്യൂ (First Value) മാത്രം എടുത്ത്, ഈ പ്രക്രിയ ഒരു Promise പോലെ അവസാനിപ്പിക്കുക" എന്ന് പറയാനാണ് നമ്മൾ ഇവിടെ firstValueFrom ഉപയോഗിക്കുന്നത്.

```javascript
function initializeAuth() {
  const auth = inject(Auth); // 1. നമ്മൾ ഉണ്ടാക്കിയ Auth സർവീസിനെ ഇവിടെ ഇഞ്ചക്റ്റ് ചെയ്യുന്നു.
  
  return firstValueFrom(auth.fetchCurrentUser()) // 2. fetchCurrentUser() തരുന്ന Observable-ൽ നിന്നുള്ള ആദ്യത്തെ റിസൾട്ട് വാങ്ങി അതിനെ ഒരു Promise ആക്കുന്നു.
    .catch(() => null); // 3. സെർവറിൽ നിന്ന് എറർ വന്നാൽ (യൂസർ ലോഗിൻ അല്ലെങ്കിൽ) ആപ്പ് ക്രാഷ് ആകാതെ, 'null' റിട്ടേൺ ചെയ്ത് സൈലന്റ് ആയി വിടുന്നു.
}
```


🔁 ഇതിന്റെ യഥാർത്ഥ ഫ്ലോ (App Start-up Flow):

1. യൂസർ ബ്രൗസറിൽ വെബ്‌സൈറ്റ് ഓപ്പൺ ചെയ്യുന്നു.

2. ആപ്പിന്റെ സ്ക്രീൻ കാണിക്കുന്നതിന് മുൻപ് ആംഗുലർ ഈ initializeAuth() ഫങ്ക്ഷൻ റൺ ചെയ്യുന്നു. //  check app.config.ts 

3. അത് നേരെ ബാക്കെൻഡിലെ /api/auth/me എന്ന യൂആർഎല്ലിലേക്ക് ഒരു കോൾ വിടുന്നു.

4. ലോഗിൻ ചെയ്തിട്ടുണ്ടെങ്കിൽ: സെർവർ യൂസർ വിവരങ്ങൾ തരികയും അത് _currentUser സിഗ്നലിൽ സേവ് ആവുകയും ചെയ്യും.

5. ലോഗിൻ ചെയ്തിട്ടില്ലെങ്കിൽ (Error വന്നാൽ): .catch(() => null) ഉള്ളതുകൊണ്ട് ആപ്പ് തടസ്സപ്പെടാതെ മുന്നോട്ട് പോകും (സിഗ്നലിൽ null ആയി തുടരും).

6. ഈ ചെക്കിങ് കഴിഞ്ഞ ഉടൻ തന്നെ ആംഗുലർ ആപ്പ് സ്ക്രീനിൽ തെളിയും.
ഇത് ചെയ്യുന്നത് വഴി യൂസർ പേജ് റിഫ്രഷ് ചെയ്താൽ പോലും ലോഗിൻ സ്റ്റേറ്റ് നഷ്ടപ്പെടാതെ ഓട്ടോമാറ്റിക് ആയി ലോഗിൻ ആയിത്തന്നെ ഇരിക്കും!

Generics ഇവിടെ എന്തിനാണ് ഉപയോഗിച്ചത് എന്ന് വ്യക്തമായി മനസ്സിലാക്കാൻ, ആദ്യം ഇത് ഉപയോഗിച്ചില്ലെങ്കിൽ നമ്മൾ എത്രമാത്രം കഷ്ടപ്പെടേണ്ടി വരുമായിരുന്നു എന്ന് നോക്കാം.

Generics (<T>) ഇവിടെ ഉപയോഗിച്ചില്ലായിരുന്നെങ്കിൽ എന്ത് സംഭവിക്കുമായിരുന്നു?

നിങ്ങളുടെ ബാക്കെൻഡ് തരുന്ന റെസ്പോൺസ് നോക്കൂ. എല്ലാ റിക്വസ്റ്റിലും statusCode, message, success എന്നിവ ഒരുപോലെയാണ്. എന്നാൽ ഉള്ളിലെ data മാത്രം മാറിമറിയുന്നു.
Generics ഇല്ലായിരുന്നെങ്കിൽ, നിങ്ങൾക്ക് ഓരോ ഫംഗ്ഷനും വേണ്ടി ഇതുപോലെ വെവ്വേറെ 4 ഇന്റർഫേസുകൾ എഴുതേണ്ടി വരുമായിരുന്നു:
typescript
// 1. യൂസർ ലിസ്റ്റിന് വേണ്ടി മാത്രം
interface GetUsersResponse {
  statusCode: number; success: boolean; message: string;

}

interface AddUserResponse {

}

// 3. ഡിലീറ്റ് ചെയ്യുമ്പോൾ
interface DeleteUserResponse {

}
Use code with caution.
നോക്കൂ, ഒരേ കോഡ് തന്നെ വീണ്ടും വീണ്ടും എഴുതേണ്ടി വരുന്നു (Code Duplication). ഇത് ഒഴിവാക്കാനാണ് ApiResponse<T> എന്ന ഒരൊറ്റ Generics ഇന്റർഫേസ് നമ്മൾ ഉണ്ടാക്കിയത്.

ഇനി ഈ കോഡ് ഓരോ വരിയായി കൃത്യമായി മനസ്സിലാക്കാം:

typescript
export interface ApiResponse<T> {
  statusCode: number;
  data: T;          // <-- ഇവിടെ 'T' എന്ന് കൊടുത്തതുകൊണ്ട് ഇതിലേക്ക് ഏത് ഡാറ്റയും വരാം.
  message: string;
  success: boolean;
}
Use code with caution.
ഇനി താഴെയുള്ള ഫംഗ്ഷനുകളിൽ ഈ T എങ്ങനെയാണ് മാസ്ക് മാറ്റുന്നത് എന്ന് നോക്കാം:

1. getUsers() — യൂസർമാരുടെ ലിസ്റ്റ് എടുക്കാൻ

typescript
getUsers(): Observable<ApiResponse<User[]>> {
  return this.http.get<ApiResponse<User[]>>(this.apiUrl);
}
Use code with caution.
• ഇവിടെ എന്ത് സംഭവിക്കുന്നു: നമ്മൾ ApiResponse<User[]> എന്ന് കൊടുത്തു. അതായത്, T എന്ന സ്ഥാനത്ത് User[] (Array of Users) വരണം എന്ന് TypeScript-നോട് പറഞ്ഞു.
• ഗുണം: കമ്പോണന്റിൽ നമ്മൾ ഈ ഫംഗ്ഷൻ സബ്‌സ്‌ക്രൈബ് ചെയ്യുമ്പോൾ, res.data എന്നത് ഒരു ലിസ്റ്റ് (Array) ആണെന്ന് ആംഗുലറിന് കൃത്യമായി മനസ്സിലാകും. നമുക്ക് അതിൽ .map() അല്ലെങ്കിൽ forEach ഒക്കെ ധൈര്യമായി ഉപയോഗിക്കാം.

2. addUser() — പുതിയ യൂസറെ ചേർക്കാൻ

typescript
addUser(userData: ...): Observable<ApiResponse<User>> {
  return this.http.post<ApiResponse<User>>(this.apiUrl, userData);
}
Use code with caution.
• ഇവിടെ എന്ത് സംഭവിക്കുന്നു: ഇവിടെ നമ്മൾ ApiResponse<User> എന്നാണ് കൊടുത്തത് ([] ഇല്ല). അതായത് T എന്ന സ്ഥാനത്ത് ഒരൊറ്റ User ഒബ്ജക്റ്റ് മാത്രം.
• ഗുണം: പുതിയ യൂസറെ ക്രിയേറ്റ് ചെയ്തു കഴിഞ്ഞാൽ ബാക്കെൻഡ് ആ പുതിയ യൂസറുടെ ഡാറ്റ മാത്രം തിരിച്ചു തരും. res.data.name എന്ന് അടിച്ചാൽ ടൈപ്പ്സ്ക്രിപ്റ്റ് തെറ്റ് കാണിക്കില്ല, കാരണം അതിൽ ഒരു യൂസർ ഉണ്ടെന്ന് അതിനറിയാം.

3. deleteUser() — യൂസറെ ഡിലീറ്റ് ചെയ്യാൻ

typescript
deleteUser(id: number): Observable<ApiResponse<void>> {
  return this.http.delete<ApiResponse<void>>(`${this.apiUrl}/${id}`);
}
Use code with caution.
• ഇവിടെ എന്ത് സംഭവിക്കുന്നു: ഡിലീറ്റ് ചെയ്യുമ്പോൾ ബാക്കെൻഡിൽ നിന്ന് ഡാറ്റയൊന്നും തിരിച്ചു വരേണ്ടതില്ല. അതുകൊണ്ട് T എന്ന സ്ഥാനത്ത് നമ്മൾ void (ഒന്നുമില്ല) എന്ന് കൊടുത്തു.
• ഗുണം: ഇതിനുള്ളിൽ data ഒന്നും ഉണ്ടാകില്ലെന്ന് ടൈപ്പ്സ്ക്രിപ്റ്റിന് മനസ്സിലാകും.

ഒരു ചെറിയ സംശയം: getDashboardStats()-ൽ എന്തുകൊണ്ട് Generics ഉപയോഗിച്ചില്ല?

നിങ്ങൾ ശ്രദ്ധിച്ചോ എന്ന് അറിയില്ല, ഒന്നാമത്തെ ഫംഗ്ഷനായ getDashboardStats()-ൽ ApiResponse<T> അല്ല ഉപയോഗിച്ചിരിക്കുന്നത്, പകരം StatsResponse ആണ് ഉപയോഗിച്ചിരിക്കുന്നത്.
typescript
export interface StatsResponse {
  statusCode: number;
  data: {
    stats: DashboardStats;
    recentUsers: RecentUser[];
  };
  message: string;
  success: boolean;
}
Use code with caution.
കാരണം: ഡാഷ്‌ബോർഡിന്റെ ബാക്കെൻഡ് റെസ്പോൺസ് ഘടന വളരെ സങ്കീർണ്ണമാണ് (അതിനുള്ളിൽ stats, recentUsers എന്നിങ്ങനെ രണ്ട് വ്യത്യസ്ത സാധനങ്ങൾ ഒന്നിച്ച് വരുന്നുണ്ട്). അതിനെ എളുപ്പത്തിൽ ഒരു T വെച്ച് മാത്രം സൂചിപ്പിക്കാൻ പറ്റാത്തതുകൊണ്ട്, അതിന് വേണ്ടി മാത്രം നമ്മൾ ഒരു പ്രത്യേക ഇന്റർഫേസ് (StatsResponse) ഉണ്ടാക്കി ഉപയോഗിച്ചു.

ചുരുക്കത്തിൽ:

ഈ ഫയലിൽ Generics ഉപയോഗിച്ചതിന്റെ ഒരേയൊരു ലക്ഷ്യം: statusCode, message, success എന്നീ ഫീൽഡുകൾ വീണ്ടും വീണ്ടും എഴുതി സമയം കളയാതെ, ഒരൊറ്റ ബോക്സ് (ApiResponse) ഉണ്ടാക്കി അതിലേക്ക് ആവശ്യാനുസരണം

# why void in ngOnInit()

ngOnInit എന്നത് ഒരു കമ്പോണന്റ് ലോഡ് ആകുമ്പോൾ ആംഗുലർ തനിയെ വിളിക്കുന്ന ഒരു ഫംഗ്ഷൻ മാത്രമാണ്. ആംഗുലറിന് ഇതിൽ നിന്ന് യാതൊരു വാല്യൂവും തിരിച്ചു കിട്ടേണ്ട ആവശ്യമില്ല. അതുകൊണ്ട് തന്നെയാണ് അതിന് : void എന്ന് കൊടുക്കുന്നത്.
